# Клиентский путь

## Схема

```
/start → приветствие ─┬─ «Что покрывает страховка» → описание → «Рассчитать»
                      └─ «Рассчитать стоимость»
                               │
              «Как указать авто?»  [VIN] [Госномер]  (можно сразу прислать текстом — распознаём оба)
                 │                        │
          проверка формата        госномер → VIN (сервис 1)
                 │                 ├─ не найден → просим VIN
                 │                 ├─ несколько → выбор по хвосту VIN или ввод VIN
                 │                 └─ один
                 └────────┬────────┘
                  VIN → марка/модель/год/двигатель/КПП (сервис 2)
                   ├─ не найден → марка+модель → год (ввод клиента)
                   └─ найден → карточка «Это ваш автомобиль?»
                        [Да] [Нет, исправить → ручной ввод] [Ввести VIN вручную*]
                                   │
                              пробег (всегда от клиента)
                                   │
                   телефон (request_contact) [Поделиться] [Пропустить]
                                   │
           скоринг в фоне: AI + поиск → прайсинг; «живое» сообщение со статусом
                                   │
           предложение НОВЫМ сообщением (push) — цена за год и помесячно
             [За год] [Помесячно] [Изменить данные] [Что покрывает]
                                   │
                телефон обязателен (если пропущен) → платёж → страница виджета
                                   │
                webhook эквайера → «Оплата прошла», номер полиса / «Не прошла» + повтор
```

\* «Ввести VIN вручную» показываем только, если VIN найден по госномеру.

## Принятые решения

**Телефон** запрашиваем после подтверждения автомобиля и до скоринга, с кнопкой «Пропустить». Цену показываем в любом случае, а при покупке номер обязателен. Для уведомлений номер не нужен: бот пишет пользователю по `user_id` в MAX.

**VIN является ключом скоринга.** Госномер служит только способом найти VIN.

**VIN, найденный по госномеру, маскируем** (`XW8*********12345`). Иначе бот превратится в сервис «узнай VIN по чужому номеру».

**Марка, модель, год и пробег хранятся как набор утверждений с источником**: `client`, `plate_service`, `vin_service`, `ai_enrichment`. Ничего не перезаписываем. В прайсинг уходят все утверждения и список расхождений, например `year: vin_service=2014, client=2015`.

**Проверка телефона.** Используем HMAC-SHA256 от `vcf_info` с токеном бота в качестве ключа. Совпадение с `hash` подтверждает, что номер принадлежит аккаунту. Контакт, присланный не кнопкой (без `hash`) или чужой (не совпадает `max_info.user_id`), не принимаем. Кодировка `hash` в документации не указана, поэтому проверяем и hex, и base64. Если подпись не сошлась, номер сохраняется как неподтверждённый, а событие пишется в лог. Это нужно сверить на реальном MAX.

**«Живой» статус** сделан как правка одного сообщения не чаще раза в 2 секунды: у MAX лимит 2 правки в секунду на диалог. Фразы меняются по этапам прогресса прайсинга.

**Готовое предложение отправляется новым сообщением**, а не правкой статуса. Правка не даёт push, а новое сообщение даёт, поэтому пользователь, закрывший чат, узнает о готовом расчёте.

**Кнопки вопросов «замораживаются» после ответа**: клавиатура убирается, под текстом появляется выбранный вариант. Кнопки из прошлых расчётов (после `/start`) отвечают «Это сообщение устарело».

**Оплата.** Факт оплаты определяем только по серверному webhook эквайера с проверкой подписи, а не по возврату со страницы оплаты. Повторное уведомление обрабатывается идемпотентно.

## Открытые вопросы

- Какие ещё поля нужны прайсингу: тип использования (такси, каршеринг), гарантия производителя и т. п.
- Формулировки оферты и покрытия, политика ПДн.
- Допустимость сервисного сообщения «предложение готово» по правилам MAX (п. 1.5). По смыслу это ответ на запрос пользователя, но формально стоит уточнить у платформы.
- Мини-приложение (`open_app`) с виджетом CloudPayments внутри MAX вместо внешней страницы.
